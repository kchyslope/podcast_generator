# Demo UI for Podcast Generator — Design

## Purpose

`podcast_generator` is a GitHub Action ([action.yaml](../../../action.yaml)) that reads a `feed.yaml` file describing a podcast and its episodes, and generates a `podcast.xml` RSS feed from it ([feed.py](../../../feed.py)). The project currently has no UI — it's a headless Docker action.

This project adds a **static demo UI**: a self-contained web app that lets someone edit podcast/episode data in a form and see, live, both (a) what the podcast would look like in a real podcast app, and (b) the exact RSS/XML feed the Action would generate. Its purpose is demonstration — showing off what the tool produces — not a replacement for the Action itself.

## Architecture & Location

- New folder `demo-ui/` at the repo root, fully self-contained (own `package.json`, `node_modules`, build config). It does not modify or depend on the Python action, Dockerfile, or entrypoint.
- Built with **React + Vite**. No backend — everything runs client-side in the browser. `npm run dev` serves it locally; `npm run build` produces a static bundle that could be hosted anywhere (e.g. GitHub Pages) in the future, though deployment is out of scope for this spec.
- Layout: a two-pane screen — **Editor** on one side, **Live Preview** on the other. Any edit in the Editor immediately updates both preview views (no save/submit step).

## Data Model & State

A single podcast object held in React state (e.g. via `useState` at the `App` level), shaped to mirror `feed.yaml` exactly:

```
{
  title, format, subtitle, author, description, image, language, link, category,
  item: [
    { title, description, duration, published, file, length }
  ]
}
```

On first load, state is seeded with **10% Happier** as the demo podcast: real title, host (Dan Harris), and description, with 2-3 real-sounding episode titles/descriptions. Since the actual 10% Happier audio files can't be legally rehosted, each episode's `file` URL points at a small public-domain/sample audio clip so playback still works in the demo — the metadata is real, the audio is a stand-in.

## Editor Pane

A form covering:
- Podcast-level fields: title, format, subtitle, author, description, image URL, language, link, category.
- Episode list: add / edit / remove episodes, each with title, description, duration, published date, audio file URL, and file length.

Every field is a controlled input bound to the shared podcast state; changes propagate immediately, no explicit "apply" action.

## Preview Pane

Tab-switchable between two views:

1. **App preview** — styled to resemble a real podcast app (artwork, episode list with play buttons, duration/pubdate), not a plain data dump. Episodes render a native `<audio>` element wired to the episode's file URL for playback where available.
2. **Feed XML** — the raw generated `podcast.xml`, shown as read-only text. Generated by a JS function `generateFeedXml(podcast)` in `demo-ui/src/lib/generateFeed.js` that ports `feed.py`'s exact element structure (same tags, same nesting, same `itunes:*` namespaces) so the demo output matches what the real Action would produce for the same data. This keeps the demo honest — it's not just a mockup, it's the actual algorithm.

## Attribution

Since the demo uses 10% Happier's real branding and metadata (with substitute placeholder audio, not the actual episode files), the UI displays a small, visible attribution note — e.g. "Demo content based on 10% Happier, hosted by Dan Harris. Not affiliated; audio is a placeholder, not the original episode." This is shown persistently in the UI (e.g. a footer note near the preview pane), not buried in code comments.

## Out of Scope

- No backend / no reuse of the actual Python `feed.py` at runtime (JS port only).
- No persistence — edits are in-memory only, lost on refresh.
- No deployment/hosting setup (e.g. GitHub Pages) — can be a future addition.
- No changes to the existing GitHub Action, Dockerfile, or entrypoint.

## Testing

Manual verification: run `npm run dev`, confirm the demo podcast loads pre-filled, edit fields and confirm both preview panes update, and spot-check that the generated XML structure matches `feed.py`'s output shape for equivalent input data.
